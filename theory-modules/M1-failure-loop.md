# M1 失败闭环模块

> **来源论文**: APO/ProTeGi (arXiv:2305.03495, EMNLP 2023) + SkillForge (arXiv:2604.08618, SIGIR 2026)
> **依赖**: 无
> **适用**: 所有档位（最基础的模块，建议最先选配）

---

## 论文核心主张

- **APO/ProTeGi**: 失败样本 → 语言批评（文本梯度）→ 定向改写 → 验证，形成四步闭环；改写对象是外部状态（规则/SOP），不动模型权重。
- **SkillForge**: 企业实战发现大量失败源于「澄清不足」与「风格规范」而非模型能力；失败应四维归因。

## AI 可解析核心

### ① 失败治理的能力契约 (Capability Contract)

> EVO-CORE 对失败治理的具体载体保持中立，只约定必须满足的三大能力契约：

1. **契约 ①：结构化强制 (Structured Recording)**  
   任何失败/踩坑记录必须具备固定字段结构，解析器**严格校验字段数**，缺列/多列即跳过并告警，杜绝格式漂移引发级联统计污染。
2. **契约 ②：根因可归因 (Root-Cause Attribution)**  
   每条失败的根因必须归入且仅归入四维之一（`[Knowledge]/[Tool]/[Clarification]/[Style]`），使失败分布可量化、可定向改进。
3. **契约 ③：复发可度量 (Recurrence Measurability)**  
   必须统计「处置后同类问题是否复发」，复发率超阈值（30%）触发处置质量复盘，避免「改了不知道有没有用」。

---

### ② 开放式选型参考谱系 (Implementation Spectrum)

| 谱系档位 | 适用场景 | 典型载体参考（仅作启发，不作强制） |
|---|---|---|
| **极简谱系 (Minimal)** | 单机、人眼直读、`grep` 毫秒级检索 | 纯文本/管道分隔单文件（如 `fail_log.txt`） |
| **标准谱系 (Standard)** | 个人端侧、需四维分布与复发率统计 | 结构化单文件 + 本地诊断脚本（自动四维雷达 + 复发率） |
| **企业谱系 (Advanced)** | 多服务高并发、需全链路追踪 | 分布式追踪系统（OpenTelemetry/Sentry/ELK）+ 实时质量大盘 |

---

### ③ 失败日志格式（9 列，管道分隔）

```
| 日期 | 任务 | 失败事实 | 根因(四维前缀) | 成功方案 | 处置状态 | 复发计数 | 风险级 | 来源 |
```

- **处置状态枚举**: open / patched / verified / recurs / legacy
- **风险级枚举**: L1(环境波动) / L2(单次) / L3(复发≥2) / L4(高危:凭据/SSO/金钱/不可逆)
- **来源枚举**: manual / cron / user-correction / legacy

### ④ 四维归因判定规则（根因列必须且仅归入一维）

| 前缀 | 判定条件 |
|---|---|
| `[Knowledge]` | 知识缺失/过时：找不到信息、信息本身错误 |
| `[Tool]` | 工具/参数/解析错误：API 报错、格式错位、路径错 |
| `[Clarification]` | 澄清缺失：未查证先假设、上下文不明就执行 |
| `[Style]` | 规范未循：未加载 SOP、格式漂移、未按流程 |

### ⑤ 统计口径与阈值

- **四维分布** = 对根因列前缀做 Counter
- **复发率** = 复发标记数 / (patched + verified + 复发数) × 100%
- **告警阈值**: 复发率 > 30% 触发处置质量复盘

### ⑥ 解析器硬约束

- 必须**严格校验 9 列**；缺列/多列的行跳过并告警（防格式漂移级联污染）
- 复发计数必须纯数字提取（防止把风险级 `L1` 误当复发 1 次）

## 适用场景

- 任何想"从失败中学习"的 Agent——本模块是其他模块（M3/M4）的地基。
